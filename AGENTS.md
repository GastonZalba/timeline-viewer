# AGENTS.md — Instrucciones para agentes de código

## Qué es este proyecto

TimelineViewer es un **componente UI autónomo** que muestra artículos de noticias como un stack de tarjetas superpuestas con una vista de timeline expandible. Se distribuye como un paquete npm independiente.

## Filosofía: Módulo autónomo

**Este componente debe funcionar de forma completamente independiente.** No depende de ningún framework (React, Vue, Angular), no usa bundler (Webpack, Vite, Rollup), y sus únicas dependencias runtime son dos peer dependencies que la aplicación principal debe incorporar: `lightgallery` (galerías de imágenes) y `ol` / OpenLayers (mapa de "Temas destacados"). Las dos se cargan lazy, solo cuando se usa la feature que las necesita.

Esto significa:

- El consumidor importa un solo archivo JS y un solo CSS
- No hay side effects globales más allá de lo necesario para los embeds sociales
- El componente se monta en cualquier `<div>` del DOM del consumidor
- No asume nada sobre el entorno del consumidor más allá del DOM del browser

## Arquitectura

**Un solo archivo TypeScript** (`src/TimelineViewer.ts`, ~7.700 líneas) + **un solo archivo SCSS** (`src/styles.scss`, ~4.300 líneas). No hay componentes separados, no hay archivos de utilidad, no hay módulos auxiliares.

### Por qué un solo archivo

El diseño es intencional: un componente autocontenido que se puede copiar, importar o incluir sin preocuparse por resolver paths de imports internos. Esto lo hace fácil de mantener, distribuir y consumir.

### Compilación

No hay bundler. El pipeline de build es: **Prettier** (format) → `tsc` (TS→JS) → `sass` (SCSS→CSS). El resultado en `dist/` es lo que se distribuye.

## Comandos

```bash
npm run build        # Formatea + Build completo (TS + SCSS)
npm run build:ts     # Solo TypeScript
npm run build:css    # Solo SCSS
npm run format       # Formatea código con Prettier
npm run format:check # Verifica formato sin modificar
npm run watch          # Watch mode (TS + SCSS) + dev server en :3010
npm start            # Solo dev server en :3010
npm test             # test:unit + test:e2e
npm run test:unit    # Build de TS + suite jsdom (node:test, sin browser)
npm run test:e2e     # Suite Playwright (Chromium) contra el server de ejemplo
```

El `build` ejecuta Prettier automáticamente antes de compilar.

### Tests

Hay dos suites, y la separación es deliberada:

| Suite | Runner | Corre | Qué cubre |
|---|---|---|---|
| `test/*.test.js` | `node:test` + jsdom | `npm run test:unit` | DOM, markup, estado y lógica: qué nodos existen, qué botones están deshabilitados, aritmética de páginas, resets de cursor, `_findScrollContainer` |
| `e2e/*.spec.js` | `@playwright/test` | `npm run test:e2e` | Lo que jsdom no puede: geometría real, offsets de scroll, sticky bajo `fullpage`, requests al servidor |

Reglas que costan descubrir y conviene no romper:

- **No escribir tests sin que lo pidan.** Un cambio de comportamiento se valida corriendo las suites que ya existen (`npm run test:unit`, `npm run test:e2e`) y reportando el resultado, no agregando casos: escribirlos cuesta mucho más que el cambio que los motivó. Los tests nuevos (o editar los existentes para cubrir algo nuevo) solo cuando el usuario los pide explícitamente. Si una suite queda en rojo por un cambio del consumidor —por ejemplo `example/filters.js`, que es suyo y se tunea seguido— avisarlo y preguntar, no "arreglar" el test por cuenta propia.
- **Los tests jsdom importan `dist/TimelineViewer.js`, no `src/`.** Se prueban los tipos distribuidos y el consumer real, y no hace falta transpilar TS para testear. Por eso `test:unit` corre `build:ts` antes: si se toca `src/` hay que rebuildar, y `dist/` nunca se edita a mano (ver "Qué NO hacer" #11).
- **El import de lightGallery necesita un hook de resolución.** `dist/TimelineViewer.js` importa `lightgallery/plugins/thumbnail` y `lightgallery/plugins/zoom`, que son specifiers de browser/bundler: el importmap del demo los resuelve, pero el resolver de Node no (sin `exports` map → `ERR_UNSUPPORTED_DIR_IMPORT`). `test/helpers/resolve-lightgallery.js` es un `resolve` hook que le da a Node el mismo mapeo, apuntando a los mismos `.es5.js`. **No cambiar esos imports para contentar al runner**: el contrato es del consumidor.
- **Los helpers viven en `test/helpers/`, así que `node --test test/` los reporta como dos "ok" sin subtests.** Es ruido esperado, no un test roto. (Por eso los specs de Playwright están en `e2e/` y no en `test/`: si colgaran de `test/`, el runner de Node los ejecutaría y fallarían fuera de su runner.)
- **`IntersectionObserver` no existe en jsdom** y se stubea en `test/helpers/dom.js`. El componente solo lo construye con el timeline expandido (`_setupTimelineObserver`); `_setupObserver` es código muerto y no se llama nunca.
- **jsdom no tiene motor de layout**: `getBoundingClientRect()` devuelve ceros y `scrollTop` es inerte. Por eso todo lo que es geometría o scroll vive en Playwright, no en la suite jsdom.
- **Los tests de Playwright son herméticos**: `e2e/helpers/network.js` intercepta el importmap de jsDelivr, sirve lightGallery y `ol` desde el `node_modules` local, stubbea los tiles de `tile.openstreetmap.org` con un PNG 1x1, y aborta todo lo demás externo (imágenes de `picsum`). Corren sin internet.
- **En la suite jsdom, las filas de control también son `.timeline-item`.** El source arma cada fila como `'timeline-item timeline-<x>-item'`, así que los selectores de artículos tienen que excluir `.timeline-paginator-item`, `.timeline-status-item`, `.timeline-load-more-item` y `.timeline-footer-item` o se cuelan como artículos. El id de un artículo tampoco está en la fila: está en `.timeline-card[data-card-id]` (o, para los ítems `capturado: false`, en el texto de `.card-not-captured-id`).
- **`test-results/` y `playwright-report/` están en `.gitignore`.** El primer browser se baja una vez con `npx playwright install chromium`.
- Los tests del demo usan flags de `example/script.js`: `?flat`, `?pagination`, `?full`, `?expanded`, `?api`, `?many`, `?sininternos`. Ojo con `?pagination` **sin** `?flat`: el modo `content` arranca en la primera taxonomía, que tiene 9 ítems contra un `itemsPerPage` de 10, o sea una sola página y sin paginador (comportamiento correcto). Para ver paginación en modo local hay que ir a `?flat` o elegir "Ver todo" en el selector. El demo siempre lleva `stateInUrl: true`, así que la suite e2e ve los `tv_*` en la barra de direcciones: `test/url-state.test.js` (jsdom, con los helpers `setSearch` / `currentParams` / `tvParams` de `test/helpers/dom.js`) y el bloque "estado en la URL" de `e2e/filters.spec.js`. El test de persistencia de filtros **ya no puede esperar que un grupo que no es `persist` se pierda al recargar**: con `stateInUrl` vuelve por la URL.
- **`?many` es el banco de pruebas del filtro `select`** (y es el motivo de que exista el flag): le agrega a los ítems un campo sintético `topicos_demo` con 400 valores distintos y le inyecta el `select` de ese campo. El mock tiene solo 19 ítems, así que un tema por ítem daría 19 valores y no probaría nada: cada ítem lleva `MANY_PER_ITEM` temas del pool para que entre todos cubran los 400. Es **solo modo local** (en API los ítems los manda el server), y combinable con `?flat`/`?expanded`/`?full`. Sirve para ver la ventana de 50 filas, el scroll que la agranda, y la búsqueda con acentos/case y el teclado. **Dos ítems quedan fuera de esa repartición**, con `topicos_demo: null` (`MANY_WITHOUT_FIELD`): uno está en la primera taxonomía, que es la que abre el demo en modo `content`, así que el bucket se ve sin cambiar de taxonomía. Por eso el grupo declara `allowEmpty: true` y ofrece el **"Sin valor"** al final, que la librería ya soportaba para un `select` (bucket vacío = token `'null'`, y sale aunque el ítem mande `[]` en vez de `null` no cuenta: el token sale de `null` o del campo ausente). `MANY_PER_ITEM` se calcula sobre los ítems que **sí** llevan el campo, y el offset del pool corre sobre un contador denso de esos ítems, no sobre la posición en el array: los dos sin campo están en medio del listado y multiplicar la posición dejaría un hueco de temas sin cubrir.

El `build` ejecuta Prettier automáticamente antes de compilar.

## Qué NO hacer

Estas son restricciones críticas. Violarlas rompe la filosofía del módulo:

1. **NO agregar bundlers** (Webpack, Vite, Rollup, esbuild). La compilación es `tsc` + `sass` + un paso de copia del plugin zoom vendado (`build:lgzoom`).
2. **NO partir el archivo TS en múltiples archivos**. Todo va en `TimelineViewer.ts`.
3. **NO agregar frameworks** (React, Vue, Svelte, etc.). Es vanilla DOM.
4. **NO agregar dependencias runtime**. `lightgallery` y `ol` son peer dependencies, no se incluyen en el bundle (se cargan lazy con un `import()` dinámico cuando se usa la galería o el mapa).
5. **NO cambiar el formato de salida**. El resultado es un ES module con default export de la clase `Timeline`.
6. **NO agregar side effects globales** al importar el módulo (salvo los SDKs de embed que se cargan bajo demanda).
7. **NO cambiar la interfaz pública** (`TimelineOptions`, `TimelineItem`, `ItemTema`) sin actualizar la documentación y los tipos.
8. **NO renombrar la clase exportada** `Timeline` ni cambiar el default export.
9. **NO modificar la estructura de datos** `TimelineItem` sin considerar que viene de un pipeline de scraping externo.
10. **NO agregar CSS que dependa de clases fuera de `.publicaciones-container`**. Todo el estilo está scoped (esa clase la agrega el constructor al `container` del consumidor; el timeline en sí vive un nivel más adentro, en `.publicaciones-timeline-section`).
11. **NO modificar manualmente los archivos de `dist/`**. Son artefactos generados por el build (`npm run build`). Cualquier cambio se hace en `src/` y se regenera.

## Convenciones de código

### Formato

Se usa **Prettier** con esta configuración (`.prettierrc`):

- Semicolons: siempre
- Quotes: single quotes
- Trailing commas: ninguna
- Indentación: 2 espacios
- Line width: 120

El `build` ejecuta `format` automáticamente. Para formateo manual: `npm run format`.

### TypeScript

- **Target**: ES2020, módulos ES2020, `moduleResolution: "bundler"`
- **Modificadores**: Todos los métodos internos son `protected` con prefijo `_` (ej: `_buildLayout`, `_renderAll`). Esto permite subclasear si es necesario.
- **Propiedades de clase**: Se declaran en la clase (no en el constructor). Se inicializan en el constructor.
- **Templates HTML**: Se construyen con `innerHTML` y template literals. No se usa `createElement` encadenado.
- **Event listeners**: Se bindan en `_init()` o dentro de `_createTimelineItem()`. Se usan `addEventListener` directos.
- **Tipado estricto**: `strict: true` en tsconfig. No usar `any`.

### SCSS

- **Namespace CSS**: Todo el archivo está anidado bajo `.publicaciones-container` (la clase que el constructor agrega al `container` del consumidor), y ahí cuelgan tanto la vista del mapa general (`.publicaciones-fullmap-section`) como la base de `.timeline-item`. El timeline en sí —`.featured-row`, `.timeline-container`, filtros, etc.— vive un nivel más adentro, en `.publicaciones-timeline-section`. Las propiedades CSS custom usan el prefijo `--tv-` (ej: `--tv-bg-primary`, `--tv-accent`) y están declaradas en `:root` al inicio del archivo.
- **Nomenclatura BEM-like**: `.card-body`, `.card-title`, `.timeline-date-col`, `.featured-card`.
- **Loop `@for`**: Las posiciones de las tarjetas featured se generan con `@for $i from 1 through 10` en SCSS.
- **Selectors modernos**: Se usa `:has()` para estilos condicionales.

### Strings

- **Todo el texto visible al usuario está en español** (`es-ES`). Fechas, labels, botones, mensajes vacíos.
- **Los nombres de campos del data model también están en español** (`nombre_fuente`, `resumen_ia`, `tonos_sociales`, etc.). Esto es porque el componente se integra con un pipeline de scraping en español.

## Modelo de datos

El componente consume **taxonomías medias**: un array de `ContentGroup`, cada una con un `label` y su propio listado de `TimelineItem`. Los `label` son las opciones del `<select>` que se muestra al expandir el timeline; el timeline, los filtros y la paginación quedan acotados al grupo seleccionado. El contador del botón de expandir y las featured cards colapsadas usan el **pool completo** (todas las taxonomías).

```typescript
interface ContentGroup {
  label: string;           // Nombre de la taxonomía (texto plano, opción del selector)
  items: TimelineItem[];   // Artículos de la taxonomía (mismo formato que la lista plana de siempre)
}
```

`TimelineOptions.content?: ContentGroup[]` tiene prioridad sobre `TimelineOptions.items?: TimelineItem[]`, que queda como **alias legacy**: sin `content` el componente se comporta exactamente como antes y **no renderiza ningún selector**. La estructura interna de `TimelineItem` es plana (no jerárquica), diseñada para un pipeline de scraping de noticias:

```typescript
interface TimelineItem {
  id: number | string;
  nombre_fuente: string;        // Titular del artículo
  resumen_ia: string | null;    // Resumen generado por IA (null = no se muestra)
  fecha_publicacion: string;    // YYYY-MM-DD
  fecha_scrapeo: string;        // ISO datetime
  tonos_sociales: string[];     // Tono(s) social(es) del artículo (valores únicos de temas)
  fuente_institucional: string | null; // Nombre del medio
  tipo_fuente: string | null; // Tipo de fuente (null = sin tipo; ver valores en README)
  es_oficial: boolean;          // Indica si la fuente es oficial
  validado: boolean | null;     // Indica si el artículo fue validado (true/false/null = pendiente/desconocido)
  capturado: boolean;           // Indica si el artículo fue capturado (false = solo id y link_web disponibles, resto vacío)
  descartado: boolean | null;   // Indica si el artículo fue descartado (true = descartado, false = en uso, null = desconocido)
  thumbnail: string | null;     // URL de imagen principal
  link_web: string;             // URL del artículo original
  actores_principales: string[] | null;
  adjuntos: string[];            // Archivos/links adjuntos (puede estar vacío)
  screenshot: string | null;    // URL de captura de pantalla
  imagenes: { thumb: string; full: string }[] | null;  // El backend puede mandar null en vez de []
  links_videos?: string[] | null;      // Links de videos relacionados (se renderizan como embeds al expandir la tarjeta: plataformas sociales o archivos de video directo)
  has_video: boolean;           // Indica si el ítem tiene contenido audiovisual (links_videos o link_web de video)
  link_edit_entry?: string;     // URL de formulario de edición (muestra botón rojo "Editar" en la tarjeta)
  link_view_entry?: string;     // URL de la vista individual del ítem (vuelve el ID del menú de información un link y agrega el botón de compartir)
  taxonomias?: SingleTaxonomy[];  // Grupos de links de navegación del pie de la tarjeta en modo single. Opcional, y solo texto plano
  contenido: string[]; // Temas del contenido del artículo, ya clasificados (adjuntos / audio y video / imágenes). Campo sintético del pipeline
  anio_publicacion: string | null; // Año de `fecha_publicacion` ya separado (null = sin fecha). Campo sintético del pipeline
  temas: ItemTema[];            // Subtemas del artículo (id_subtema, título, resumen, tono, fecha/notas opcionales y, opcional, geom { lat, lon })
}
```

`contenido` y `anio_publicacion` son los dos campos que `example/filters.js` filtra en lugar de `fecha_publicacion` a secas: el pipeline (o el mock) los manda **ya clasificados**, para que el filtro sea un `string` (o un `'null'`) contra un `string` y no dependa de un `extract`. Por eso no se derivan en el componente ni en `example/server.js`; si se agregan o se cambian, la regla de Mock ↔ Interfaces ↔ README los tiene que cubrir en el mismo commit.

`link_view_entry` es un campo **por ítem**, no una opción del constructor: puede venir en relativa (`?id=FUE-00001`, `/articulos/FUE-00001`) y se absolutiza con `_absoluteUrl()` para compartir. También viaja en el `TimelineItemSummary` de modo API (va en `toSummary()` de `example/server.js`), porque el botón de compartir y el link del ID se renderizan en la tarjeta colapsada, antes de que exista el detalle.

`taxonomias` también es un campo **por ítem**, no una opción del constructor: el bloque de links de navegación del modo single sale del propio dato (`_appendTaxonomies(card.taxonomias)` en `_renderSingleCard`), nunca de la config. En modo API llega en el detalle (`GET {url}/:id`) y **no** en la lista paginada, porque solo se usa con `singleId`, donde el artículo ya se pide entero. `SingleTaxonomyItem.content` es `string` y siempre se escapa: el dato viene de la API (JSON), así que no admite markup ni nodos DOM. Si el detalle no se puede cargar, no hay ítem y por lo tanto no hay bloque que renderizar.

`geom` es un campo **por tema** (dentro de `ItemTema`), opcional: `{ lat: number, lon: number }` en grados. El bloque "Temas destacados" de cada tarjeta arma con él el mapa de forma lazy: `_temasLocated()` deja afuera los temas sin `geom` o con uno inválido (`_temaGeomOf` valida tipo y rango) y numera los que quedan (1-based); el toggle, los badges de la lista y el mapa salen todos de esa misma lista numerada, que es lo que mantiene el número de un badge y el de un círculo diciendo lo mismo. OpenLayers se importa con un `import()` dinámico en el primer "Ver mapa", la capa base es OSM por defecto (opción `temasMapTiles`, `''` = solo los puntos) y los mapas se destruyen en `_destroyTemasMaps()` cuando la lista se rearma o se cambia por los skeletons. Ver `## OpenLayers — mapa de temas`.

`id_subtema` es un campo **por tema** y **obligatorio**: la primary key del subtema, única en toda la colección (en el mock va de `T-000001` a `T-000040`, un contador global por orden de aparición, no por artículo). Es la identidad con la que el mapa general cruza un punto con la fila de la ficha: viaja en `GET {url}/points` como `id_subtema` (**reemplazó a `tema_index`**, que era la posición dentro de `temas` y no identificaba nada entre dos listados distintos), se pinta en cada fila como `data-id-subtema` y compone el key de `_fullMapPointKey()` junto con el id del artículo. Un backend que no lo manda deja `''`, y entonces la ficha abre sin scroll ni resaltado pero el mapa funciona igual. La posición (`data-tema-index`) sigue viva, pero solo para bindear el click de la fila con su tema: `_revealFullMapTema()` busca por `dataset.idSubtema` **comparando strings y no armando un selector**, porque el valor viene del backend.

Cada grupo del bloque renderiza como máximo `TAXONOMY_VISIBLE_LINKS` (3) links: el resto se emite en el markup como `li.card-taxonomy-extra[hidden]` y un `button.card-taxonomy-more` ("Ver más (N)" ⇄ "Ver menos", con `aria-expanded`) los muestra/oculta **por grupo**, en `_bindTaxonomyToggles(slot)` (después del `innerHTML` del `.card-taxonomies-slot`). El handler agrega la clase `expanded` al `ul.card-taxonomy-list` de ese grupo: **la visibilidad la manda el SCSS del componente** (`.card-taxonomy-extra` hidden / `.card-taxonomy-list.expanded .card-taxonomy-extra` visible), no el atributo `hidden`, porque la regla UA `[hidden]` cede ante cualquier `display` de autor (mismo motivo que obliga a `.taxonomy-row[hidden] { display: none }`). El `hidden` se mantiene en sync igual. El estado vive solo en el DOM, sin campo en la clase; `_buildTaxonomias` es puro y no bindea eventos.

**No modificar esta interfaz** sin considerar que los datos vienen de un sistema externo.

`ContentGroup` **no** es lo mismo que `SingleTaxonomy` (que agrupa _links_ de navegación bajo la tarjeta en modo single). No confundirlos ni mezclar sus campos: `ContentGroup` viene de la opción `content` y agrupa artículos del timeline; `SingleTaxonomy` viene del campo `taxonomias` del ítem y agrupa links.

Helpers que definen el scope de datos en `src/TimelineViewer.ts`:

- `_allItems()` → todos los items de todas las taxonomías. Se usa en single mode (buscar por `id`), para armar las featured cards, para el scope de "Ver todo" y para el total del contador (en modo API ese rol lo cumple `_apiCollectionTotal`, porque el pool no está en el cliente).
- `_scopeItems()` → items de la taxonomía activa, o el pool completo si `_contentIndex === ALL_TAXONOMIES_INDEX` ("Ver todo").
- `_sortBy()` → copia ordenada por el sorter activo (`_sortField` + `_sortAsc`). **Se aplica después de filtrar**: no existe un pool pre-filtrado ordenado. La comparación es **natural** (`Intl.Collator` con `numeric`, vía `_sortValue()`): las fechas ISO y los ids con ceros a la izquierda ordenan bien como texto plano, así que no hay lógica por campo. Un valor ausente es el más chico, así que en `desc` los sin valor van **últimos** y en `asc` **primeros**. El `sort` es **estable**, así que los empates conservan el orden de origen en las dos direcciones (ya **no** se hace `reverse()`: ese `reverse()` invertía el orden de los empates). Cualquier cambio acá hay que replicarlo en `sortItems()` + `sortValue()` de `example/server.js`, que es el lado servidor del mismo comportamiento (ver "Cambiar el contrato de la API").
- `_applyFilters()` calcula **los dos** conjuntos en una sola pasada: `allCards` (scope activo) y `_featuredCards` (pool completo). Las featured están ocultas en CSS cuando el timeline está expandido, así que nunca se re-renderizan al colapsar.
- `_renderRelatedCount()` → el único lugar que escribe el contador del botón de expandir (`#remaining-count` + `relatedLabel(count)`). Toma el pool sin filtrar: `_allItems().length` en local, `_apiCollectionTotal` en API. Se la llama desde `_renderAll()` y desde el `.then()` de `_ensureApiFacets()`, para poder parchear el contador cuando llegan los facets sin re-renderizar el timeline.

### Regla de oro: Mock ↔ Interfaces ↔ README

`example/mock-data.js` es la **fuente de verdad** para probar el componente. Cualquier cambio en el mock **obliga** a aplicar el mismo cambio en el mismo commit:

1. **Mock**: `example/mock-data.js` (agregar/renombrar/eliminar el campo en los 19 artículos).
2. **Interfaz**: `TimelineItem` en `src/TimelineViewer.ts`.
3. **Tipos distribuidos**: `dist/TimelineViewer.d.ts` (regenerado con `npm run build`).
4. **Documentación**: tabla de campos en `README.md` (y este documento).

No se puede modificar el mock sin actualizar interfaces y README en el mismo cambio, y viceversa.

El mock exporta **las dos formas**: `content` (los grupos por taxonomía, armados con `slice` sobre el listado completo) e `items` (la lista plana, usada por `example/server.js` para el modo API y por el flag `?flat` de `script.js`). `mockData.items` debe seguir siendo el listado completo.

## Embeds sociales — Dependencia crítica de carga

El componente carga SDKs de redes sociales **bajo demanda** cuando se expande una tarjeta. Existe una **dependencia de orden obligatoria**:

```
Instagram embed.js  →  DEBE cargarse ANTES de  Facebook SDK
```

**Por qué**: Facebook SDK setea `window.FB`. Instagram's embed.js verifica `(window.FB && !window.FB.__buffer)` al inicializar y se salta la inicialización si FB ya existe. Si se cargan en orden incorrecto, los embeds de Instagram no funcionan.

Twitter widgets.js se carga en paralelo (sin conflictos).

Ver `_preloadEmbedLibraries()` en `src/TimelineViewer.ts:5787` para la implementación exacta.

## lightGallery

Es un **peer dependency** (`^2.9.0`). El componente importa:

```typescript
import lightGallery from 'lightgallery';
import lgThumbnail from 'lightgallery/plugins/thumbnail';
import lgZoom from 'lightgallery/plugins/zoom';
```

Los tres specifiers son de browser/bundler: el consumidor los tiene que resolver (bundle propio o importmap, como hace `example/index.html`). El componente NO incluye lightGallery en su build, y `npm run build` no necesita copiar nada de `node_modules` a `dist/`.

El consumidor debe proveer lightGallery en su bundle o via importmap. Para los tests, el importmap del demo apunta a jsDelivr, pero `e2e/helpers/network.js` intercepta esas requests y sirve los mismos `.es5.js` desde el `node_modules` local, así que la suite corre sin internet.

### El zoom con la rueda (`LgWheelZoom`)

`_openLightGallery()` pasa **tres** plugins: `lgZoom`, `lgThumbnail` y `LgWheelZoom`, una clase própria del módulo que vive en `src/TimelineViewer.ts` (arriba de `Timeline`, no exportada, sin dependencia nueva). Existe porque **lightGallery 2.9 no trae zoom con rueda**: el plugin `zoom` maneja pinch (táctil), drag para panear y los íconos +/−, pero no escucha `wheel`; y el `settings.mousewheel` del core, que sí escucha, es de **navegación entre slides** con throttle de 1s, así que tiene que quedar en `false`. No hay que vendorizar ni parchear nada del peer dep para agregarlo.

Seis cosas del plugin que costaría volver a romper:

0. **El ancla del zoom es el cursor, y es estado del plugin, no un parámetro.** `zoomImage()` arma el transform a partir de `pageX`/`pageY` del plugin (`_x = offsetX - this.pageX`), y el peer dep los deja **en el centro del modal** al abrir (`afterOpen`), así que sin tocar nada la rueda escala siempre desde el medio — que era el comportamiento anterior. Lo escribe `_anchorToCursor()`, llamado en `_onWheel` después del clamp de `next` (o sea que los ticks que no hacen nada ni lo tocan) y antes del `beginZoom`. Cuatro cosas: (a) **el gate es el rect de `.lg-current .lg-image`, no el del `.lg-img-wrap`**, porque el wrap es `position: absolute` con `left/right/top/bottom: 0` + `width/height: 100%`, o sea el rect del slide entero y daría "dentro" siempre; con el cursor fuera de la imagen (caption, barra de miniaturas) no se escribe nada y el ancla sigue siendo el centro. (b) **Coordenadas mezcladas a propósito**: el gate compara `clientX/clientY` contra el rect (viewport), pero el ancla se escribe con `pageX/pageY`, que es el espacio con el que trabaja la fórmula del peer dep (`containerRect` + `zoom.scrollTop`) y en el que el `dblclick` ya deja su ancla vía `setPageCords()`. (c) **No usar `setPageCords(event)`**: hace `event.pageX || event.touches[0].pageX` y un `WheelEvent` no tiene `touches`, así que con `pageX` en `0` revienta; los dos campos son públicos en el `.d.ts` del peer dep. (d) **`zoom.positionChanged = false` antes de `zoomImage()`**: el drag y el pinch dejan ese flag en `true` y `zoomImage()` lo consulta **antes** que `pageX`/`pageY`, rehaciendo el ancla desde `left`/`top` para no mover lo que quedó arrastrado — sin limpiarlo el primer tick de la rueda tras arrastrar vuelve al centro. El `left`/`top` del drag entra igual en la fórmula, así que la posición alcanzada no se pierde. Verificado en el browser con una imagen sintética de 2000x1400 en un visor de 983x688: con el cursor al 25%/35% de la imagen, el píxel bajo el cursor se movió **1.2px** después de un zoom de 1.60x (antes del cambio eran **147px**); con el cursor en el centro el transform del wrap queda en `matrix(1,0,0,1,0,0)`, igual que antes; rueda abajo de vuelta a 1x el rect de la imagen vuelve bit a bit al de ajuste; y tras un arrastre real el tick siguiente desvía 0.2px.

1. **No reimplementa el transform.** El handler llama la API pública del plugin `zoom` (`beginZoom` + `zoomImage` + `getScale`), que es la misma que usan los íconos, así que el wrap y la imagen los sigue moviendo lightGallery: el drag, el pinch y el reset al cambiar de slide quedan intactos. La instancia del zoom se busca en `core.plugins` con `instanceof lgZoom` (`plugins` es `any[]` en el `.d.ts` del peer dep; `core.plugins` se llena en el constructor, y `initModules()` es lo último de `buildStructure()`, así que en `init()` el `.lg-outer` ya existe).
2. **El teardown sale solo** y hace falta: `_lgContainer` se reutiliza entre aperturas (`_openLightGallery` no lo vuelve a crear si ya existe), así que un listener de `wheel` a mano se acumularía. Como plugin, lo limpia el `destroy()` que el core llama vía `destroyModules(true)` en `destroy()`, que el componente ya invoca en el `lgAfterClose`.
3. **El tope del zoom es "el tamaño real de la imagen, y si no hay nada que ampliar, `LG_WHEEL_ZOOM_FALLBACK_MAX` (4)"**, y no un tope fijo. Ojo con **qué** método trae la escala real: es `getCurrentImageActualSizeScale()`, **no** `getScale(n)`, que **clampa al valor que se le pasa** —usarlo convertía al 4 en el techo de las imágenes grandes, y una captura de 1265x8012 en un visor de 632 se quedaba en 4x de sus ~12.7 reales, que es el bug que reportó el consumidor—. El piso se aplica solo si la escala real no supera 1 (`realMax > 1 && Number.isFinite(realMax) ? realMax : FALLBACK`): con un `Math.max(realMax, MAX)` el piso le gana al techo y las imágenes grandes se pixelean hasta 4x. El `Number.isFinite` cubre el `Infinity` que devuelve la escala real si la imagen todavía no tiene layout (divide por `offsetWidth === 0`), de ahí el guard de `containerRect` —lo setea `setZoomEssentials()`, que corre cuando la slide carga—. Ojo con el nombre: si el peer dep alguna vez agrega un tope propio, el 4 es de reserva, no el techo.
4. **El scroll es continuo, no por pasos**: `scale *= 1 - deltaY * LG_WHEEL_ZOOM_RATE`, con un cooldown de `LG_WHEEL_ZOOM_COOLDOWN` para la inercia del trackpad, y `deltaMode === 1` (Firefox mide en líneas, no en píxeles) normalizado a `LG_WHEEL_ZOOM_LINE_PX`. El paso por pasos de los íconos es `settings.scale: 1`, o sea 1x → 2x → 3x, y con la inercia de un trackpad un flick se come los topes de un saque: por eso la rueda no los reusa. El `preventDefault()` va siempre que haya una imagen en pantalla, no solo cuando se actúa: sin él, el primer tick de una ráfaga se escapa a la página. Con la rueda abajo en 1x no pasa nada y **no** navega slides. Un detalle heredado: el primer tick después de abrir puede caer antes de que la slide cargue y se pierde (mismo límite que los íconos +/−, que también no-op con `zoomImage` sin `containerRect`).
5. **En estado "tamaño real" la rueda no hace zoom, y eso es a propósito**: cuando el plugin `zoom` entra a su representación de tamaño real —la que activa el doble click del peer dep— cambia de modelo —el `.lg-image` queda con su tamaño natural en layout y el `!important` de `lg-zoom.css` le fuerza `scale(1)`— y deja su campo `scale` (el de la transformación) sin reconciliar, así que cualquier `zoomImage()` desde ahí mueve la imagen sin razonar la escala nueva: se ve como un salto. Por eso `_onWheel()` corta antes de calcular: para arriba no hace nada (ya es 1:1, no hay nada más que ampliar) y para abajo devuelve al ajuste con **`resetImageTranslate(index)` + `resetZoom(index)`, en ese orden y los dos**: `resetZoom()` solo no alcanza, porque no saca la clase `reset-transition-y` —el `!important` que manda el tamaño natural— ni los `width`/`height` inline, y `resetImageTranslate()` solo no alcanza, porque no limpia el `transform` inline ni reinicia `scale`/`left`/`top`. La detección **no** puede ser solo la clase `lg-actual-size` del `.lg-outer`: queda pegada entre aperturas (el contenedor se reutiliza), con lo cual el primer tick con la imagen todavía en su caja de ajuste caería en la rama equivocada; se confirma con la geometría (`offsetWidth === naturalWidth`), que en ese estado es la única que vale. Esta rama también arregla el camino viejo del doble click, que tenía el mismo salto.

### La captura a tamaño real anclada arriba (`LgWheelZoomTopAnchored`) — **revertida, no existe**

La subclase, la clase padre, la opción pública `screenshotActualSize`, sus constantes (`LG_ZOOM_ACTUAL_MIN_SCALE`, `LG_ZOOM_POLL_INTERVAL`, `LG_ZOOM_POLL_TRIES`) y las dos ramas del SCSS que la sostenían fueron revertidas a propósito en `060f3ef`, así que **el código actual no la tiene**: el screenshot abre como siempre, al ajuste, y el zoom con la rueda sigue siendo el del `LgWheelZoom` pelado.

El motivo de dejar la nota es que el diseño está documentado (y medido) en `git show de4ef4c`, así que recuperarlo es un `git show` + un port de las reglas que había abajo, no escribirlo de cero. Si se recupera: hay que devolver la opción al `.d.ts` y al README (que ya no la lista), y volver a agregar el gate de `LG_ZOOM_ACTUAL_MIN_SCALE`, que es **la** parte que no se puede recuperar de otro lado y de la que dependía el resto para no cambiar el comportamiento de las capturas que entran enteras en el visor.

Lo que sigue en el punto 5 de más arriba ("en estado tamaño real la rueda no hace zoom") sigue siendo cierto **por el otro camino**: el doble click del peer dep también entra a esa representación, así que la rama vive, pero ahora solo la atiende ese gesto.

## OpenLayers — mapa de temas

El mapa de "Temas destacados" de cada tarjeta es la segunda feature que usa un **peer dependency** (`ol`, `^10.10.0`) y la segunda que lo carga lazy. El consumidor resuelve `ol` en su bundle o por importmap (el demo lo hace con `/vendor/ol/`) y provee el stylesheet `ol.css`; el componente **nunca** lo inyecta (no agrega side effects al importar).

Lo que hay que saber:

- **La carga es lazy y por feature.** `_loadOpenLayers()` hace el `import()` dinámico de `ol/Map.js`, `View.js`, `Feature.js`, `geom/Point.js`, `geom/LineString.js`, `layer/Tile.js`, `layer/Vector.js`, `source/XYZ.js`, `source/Vector.js`, `style/Style.js`, `style/Circle.js`, `style/Fill.js`, `style/Stroke.js`, `style/Text.js`, `Overlay.js`, `control/Zoom.js`, `control/Attribution.js` y `proj.js`. Los specifiers llevan extensión `.js` porque `ol` no tiene `exports` map. El importmap del demo (`example/index.html`) mapea cada uno. Ojo: `ol` **nunca** importa con specifier bare (sus imports internos son relativos), así que el importmap existe solo para los `import()` del componente: si se saca un módulo de la lista hay que sacar su entrada del importmap, y al revés no pasa nada.
- **El toggle es puro y el mapa se monta en el primer open.** `_buildTemasMapToggleHtml()` / `_buildTemasMapBodyHtml()` solo emiten markup (y devuelven `''` si ningún tema tiene `geom`); `_bindTemasMapToggle()` es el único que escucha el click y, en el primer "Ver mapa", llama a `_mountTemasMap()`. El `requestAnimationFrame` previo es lo que deja al browser medir el canvas ya visible antes del `View.fit`.
- **Zoom siempre entero (`constrainResolution: true` del `View`).** El `ol.OlView` que arma `_mountTemasMapOn` lo declara, y es lo que hace que **todo** zoom del mapa caiga en un nivel entero: un zoom fraccionario hace que OpenLayers pinte los tiles del nivel XYZ más cercano escalados, que es exactamente la borrosidad de las capas raster. Los tres `fit` (el del montaje, `TemasMapHandle.fit()` y el de foco de un punto) **no** pasan `nearest`, así que OL constrain-ea con dirección 1 = `floor`: cada fit aterriza en el nivel entero **más lejano** que igual encuadra el extent —no en el más cercano—. Como OL 10 no tiene `zoomSnap`, la misma bandera es la que impide que rueda, pinch o doble click se salgan de zoom entero. Consecuencia para `declutter()`: `view.getZoom()` devuelve enteros, o sea que los cortes contra `TEMAS_MAP_CLUSTER_MAX_ZOOM` (12) y `TEMAS_MAP_NO_CLUSTER_MIN_ZOOM` (15) cantan con niveles reales. No sacar la opción "para ajustar mejor el fit": ese ajuste fino es justamente el que borra los tiles.
- **Marcadores = círculos con número, color por tono.** Un `ol/style/Circle` (radius `TEMAS_MAP_MARKER_RADIUS` = 9, ring negro `#0e1116`) más un `ol/style/Text` centrado con el número. No hay pines: el `style` va con `feature.setStyle()`, **no** como opción del constructor `OlFeature` (que lo ignora y cae al default cyan).
- **Spiderfy (vista cercana) y clúster (vista lejana): son los modos del mismo `declutter()`.** El modo lo elige `zoom < TEMAS_MAP_CLUSTER_MAX_ZOOM` (8) —por debajo de ese corte **no existe spiderfy**: todo grupo se pinta como un conteo y solo un punto suelto conserva su círculo con número, o sea que la vista lejana solo aglomera—, salvo que `zoom >= TEMAS_MAP_NO_CLUSTER_MIN_ZOOM` (15), donde manda el spiderfy **sin el tope de 12** (ver el bullet de la vista cercana más abajo). En el modo clúster los círculos que se solapan **no** se reparten: se pintan como un solo círculo con el conteo (ver el bullet de los clústeres más abajo). En el modo spiderfy los círculos que se solapan en pantalla se reparten alrededor del centroide (agrupamiento todos-contra-todos: un punto entra solo si está a ≤ `TEMAS_MAP_SPIDER_THRESHOLD` de **todos** los miembros del grupo, no de cualquiera — así ningún grupo pasa de ese ancho de punta a punta, y una cadena de puntos cercanos ya no se fusiona en un grupo que englobe media pantalla). La separación entre vecinos es `2 * (TEMAS_MAP_MARKER_RADIUS + TEMAS_MAP_SPIDER_GAP)` = **20px**, o sea los markers de 19.5px (radio 9 + stroke 1.5 centrado) con medio px de aire entre ring y ring: el radio del círculo del grupo crece con la cantidad (`(9 + 1) / sin(PI / n)`) y el gap solo cubre el ring. **El hit test del hover tiene que quedarse con el marker más cercano, no con el primero**: su radio es `9 + 3 = 12px`, o sea 24px de diámetro contra 20px de separación, así que las zonas de hover **se solapan** y el puntero en el medio de dos tiene que nombrar el que está arriba.
- **El desplazamiento se dibuja con una línea, y solo una línea.** Cada marker desplazado guarda en la propiedad `spider` de su feature (un `TemasMapSpider`: `line: OlLineString` y `marker: OlPoint`) las dos geometrías que hay que pintar —la línea desde la coordenada real hasta el círculo, y el círculo en su sitio nuevo—, y **el estilo de cada feature es una función** que las lee: sin eso no se puede pintar un marker fuera de su propia geometría. La línea va en el mismo negro que los rings (`TEMAS_MAP_SPIDER_LINE_COLOR`), de `TEMAS_MAP_SPIDER_LINE_WIDTH` de ancho, y **sin punta de flecha ni punto de anclaje** (a pedido: lo único que dibuja es el vínculo con el origen). Termina en el centro del círculo y se pinta **antes** que él, así que los últimos `TEMAS_MAP_MARKER_RADIUS` px quedan debajo del fill del marker y no hay que recortarla. El mapa importa `ol/geom/LineString.js` por esto y **no** importa `ol/geom/Polygon.js`: si alguna vez vuelven a hacer falta flechas, hay que sumar ese módulo a `_loadOpenLayers()`, su entrada al importmap del demo, y las constantes `TEMAS_MAP_SPIDER_ARROW_*` / `_DOT_RADIUS` a `TemasMapSpider`. Cada `moveend` empieza con `features[i].set('spider', undefined)`, que es lo que hace que un marker que ya no se solapa vuelva a su lugar (y deje de arrastrar su línea); el mismo reset limpia `cluster` y `hidden`, así que un grupo disuelto vuelve a pintar sus círculos.
- **Clúster en vista lejana: un círculo con el conteo, no un anillo.** Cuando `declutter()` corre en modo clúster (o cuando un grupo supera `TEMAS_MAP_SPIDER_MAX_GROUP` = 12, **por debajo de `TEMAS_MAP_NO_CLUSTER_MIN_ZOOM`**), el grupo se pinta como **un solo marker** en el centroide: el feature líder guarda la marca en la propiedad `cluster` (`TemasMapCluster`: `count`, `color`, `marker: OlPoint`) y el estilo lo pinta con `geometry: cluster.marker` + un `ol/style/Circle` de `TEMAS_MAP_CLUSTER_RADIUS` (14) y el número centrado; los demás miembros quedan `hidden: true` y su estilo es **`[]`** — el renderer de OL itera el array de estilos y con `[]` no dibuja nada (verificado en `node_modules/ol/renderer/canvas/VectorLayer.js`, `renderFeature`). El motivo del modo es que a zoom lejano el anillo del spiderfy crece con la cantidad (ahí es donde se rompía la UI). El grupo además está acotado a `TEMAS_MAP_CLUSTER_DISTANCE` de ancho (ligadura completa, ver el bullet del agrupamiento), así que la vista lejana reparte los puntos en **varios** clústeres chicos, cada uno sobre los markers que representa, en vez de uno solo que englobe media pantalla con el centroide en zona vacía. El **color** es el tono que comparten los miembros si todos son iguales, y `TEMAS_MAP_CLUSTER_FILL_DARK` (`#0e1116`) si el grupo es de tonos mezclados: pintar un grupo mixto del color del primero diría algo que los datos no dicen.
- **Vista cercana (`zoom >= TEMAS_MAP_NO_CLUSTER_MIN_ZOOM` = 15): el tope de 12 se apaga y nunca hay clúster.** El motivo es estructural, no estético: un clúster responde al click con un zoom de `TEMAS_MAP_CLUSTER_ZOOM_STEP`, que solo lo disuelve si los puntos estaban cerca *en pantalla* —los que comparten coordenada no se separan en ningún zoom— y esa animación además está cortada por `TEMAS_MAP_FIT_MAX_ZOOM`. A nivel calle, entonces, un clúster es un callejón sin salida: el click no hace nada y sus puntos no se pueden alcanzar. Por eso, a partir de ese zoom, **todo grupo se estira en anillo aunque pase de 12** y el conteo nunca vuelve a pintarse. El costo aceptado a propósito es que un grupo enorme tira el anillo fuera del canvas (la tarjeta mide 260px): un anillo gigante en zoom cercano es información, un conteo que no se puede abrir no.
- **El click en un clúster navega: `view.animate` con zoom + `TEMAS_MAP_CLUSTER_ZOOM_STEP` (4)**, centrado en el centroide y con tope `TEMAS_MAP_FIT_MAX_ZOOM` (15), con `TEMAS_MAP_CLUSTER_ZOOM_DURATION` (400ms) de duración: el `moveend` del animate re-corre `declutter()`, que va agrupando de nuevo en el camino. El listener de `singleclick` está bindeado **siempre**, aunque el mapa no traiga callbacks: navegar es asunto del mapa, no del consumidor, y de paso cubre los dos mapas (el de la tarjeta no tiene `onMarkerClick`… en realidad sí, pero el corte es por `target.kind`, no por la existencia de callbacks).
- **El punto abierto del mapa general nunca desarma un grupo, y dentro de un anillo crece en el sitio.** `declutter()` agrupa igual con o sin selección: no hay pre-marcado de `used[i]` que excluya al elegido, así que un punto que cae en un anillo (`spider`) **se queda desplazado en el ring** y su círculo de selección crece ahí —más grande (`TEMAS_MAP_SELECTED_RADIUS_DELTA` + `TEMAS_MAP_SELECTED_SPIDER_EXTRA_RADIUS`, o sea radio 16 con el marker base de 9), aro de 2px y **sombra proyectada**: dos discos translúcidos de `#0e1116` (`TEMAS_MAP_SELECTED_SHADE_*`, radio propio +4 y +7, 50% y 20% de tinta) con `zIndex` **-1**, o sea debajo de todos los markers, así lo que se ve de la sombra es solo la parte que cae sobre los tiles y un vecino la tapa en vez de teñirse— (`TEMAS_MAP_SELECTED_Z_INDEX`, arriba de cualquier clúster vecino)—; el radio del hit de click crece en consonancia (`TEMAS_MAP_SELECTED_SPIDER_EXTRA_RADIUS` también entra en el `radius` del target), y `TemasMapHandle.selectedSpiderCenter()` devuelve esa coordenada desplazada para que el `fit` de `_focusFullMapTema` centre el mapa donde el círculo está pintado y no en la coordenada propia, que es el centro del anillo. Lo único que la selección saca de un grupo es de un **conteo**: la rama de clúster filtra al elegido de `members` y pinta el círculo con el conteo solo si quedan 2 o más, así que a zoom lejano el punto nunca queda enterrado en un conteo y la fila de la ficha dice "está acá" (si era el único miembro del grupo no hay conteo: cada uno pinta su círculo). Los dos discos y el círculo salen del **mismo** array que devuelve `plainStyle()` (la rama del `spider` los copia uno a uno hacia la geometría desplazada, con el flag `grown` cuando el punto es el seleccionado), porque OpenLayers reparte cada estilo del feature en su bucket de `zIndex` y los ejecuta en orden ascendente. Por eso `refreshStyles()` también corre `declutter()`: la selección sí cambia quién entra en qué conteo.
- **El tope del panel de la ficha del mapa general es el bottom real de la barra, no una constante.** `.fullmap-detail` es absoluto con `max-height: calc(100vh - var(--tv-fullmap-top, 8px) - 24px)`, donde `--tv-fullmap-top` es el `getBoundingClientRect().bottom` de la toolbar, escrito por `_syncFullMapDetailTop()` (~4455): el panel empieza siempre **debajo de la barra + 8px** y no la tapa, en cualquier viewport y aunque la barra cambie de alto (fullpage: píldora sticky de ~109px; wrap del toolbar en móvil: 147px). El fallback de 8px conserva el `100vh - 32px` viejo cuando la variable no está escrita. Se mide **con la vista ya montada** —`_applyFullMapState()` (rama open) y `_openFullMapCard()` la escriben antes de mostrar el panel— porque la barra puede cambiar de alto al montar el mapa, y el listener de resize de `_bindBaseEvents()` la re-escribe **solo si `_fullMapOpen`**, para no medir en cada resize del timeline. La barra flota encima de `.publicaciones-fullmap-section` (`z-index: 2`), así que sin esta variable el panel se clampa contra el tope en viewports cortos y el inicio de la ficha (y su botón de cerrar) quedan tapados.
- **Si la ficha abre encima del punto que la abrió, la vista se corre —sin zoom—.** `_adjustFullMapViewForPanel(point, key)` (~4884) se llama al final del `.then()` de `_openFullMapCard()` y es la única corrección de este tipo: la regla es "el punto recién elegido nunca queda debajo del panel". La coordenada a despejar es la que está **pintada**: `handle.selectedSpiderCenter()` si el declutter lo dejó en un anillo, si no la `lon`/`lat` del punto pasada por `fromLonLat` (los dos casos comparten el resto del método, y el segundo es el único que espera `ol`). El choque se mide contra el rect del panel inflado por `FULLMAP_PANEL_CLEAR_PX` (16 = radio del marker 9 + delta de seleccionado 3 + extra de anillo 4), con un max-norm conservador: un falso positivo solo agrega un vuelo mínimo. Hay **dos candidatos**, en píxeles de pantalla: pasar el punto por la **derecha** del panel (la dirección esperada: el panel estorba a la izquierda) o **subirlo** por encima de su borde superior (para cuando la derecha no cabe); cada uno verifica que el círculo siga entero en el mapa —el techo del "arriba" es `max(mapRect.top, featuredRow.bottom) + clear`, porque la barra flota encima con `z-index: 2` igual que la ficha—, se elige el de **menor vuelo** con empate a la derecha, y si ninguno cabe **no se mueve nada** (un pan que saca al punto del canvas no cumple con "que quede visible"). El vuelo es `view.animate({ center, duration: FULLMAP_PANEL_PAN_DURATION })` —**solo `center`**, nunca `resolution`— con `center[0] - dx*res` / `center[1] + dy*res` (en Y el eje de pantalla está invertido respecto de la coordenada). El guard `key` recién después del `await` descarta la corrección si mientras se cargaba `ol` el usuario clickeó otro punto o cerró la ficha. **Alcance: solo el click del marker**, no `_focusFullMapTema` (ahí el `fit` centra en el viewport y en pantallas estrechas el punto puede caer bajo el panel —gap conocido, aparte—).
- **El foco de un tema de la ficha salta, sin animación.** `_focusFullMapTema()` hace `view.fit(punto, { maxZoom: TEMAS_MAP_FIT_MAX_ZOOM, duration: 0 })` y cierra con `map.renderSync()` + `handle.refreshStyles()` —el mismo par que el `fit` de apertura y el de re-apertura— porque `declutter` agrupa contra los píxeles del último frame pintado; el `moveend` del propio `fit` lo vuelve a correr, pero no se depende de cuándo llegue. Con los 400ms de vuelo que tenía se pedían tiles intermedios que OpenLayers descartaba antes de llegar (fondo roto al destino) y, en zoom cercano, el viaje se leía peor que el corte. Dos órdenes que no se pueden mover: el `refreshStyles()` inicial es el que escribe la propiedad `spider` de la que sale el destino (`selectedSpiderCenter()`, leído **después** del `await` de `ol`) y además pinta el círculo crecido antes del salto; y el `fit` va después de ese await, porque sin `ol` no hay coordenadas de vista. Los otros dos desplazamientos del mapa general siguen animados a propósito: el pan del panel (`FULLMAP_PANEL_PAN_DURATION`) y el zoom de clúster (`TEMAS_MAP_CLUSTER_ZOOM_DURATION`).
- **`targets` es lo que leen el hover y el click.** `declutter()` reconstruye en cada pasada el array `TemasMapTarget` (`kind: 'point'` con `index`/`screen`/`coord`/`radius`, o `kind: 'cluster'` con el conteo), y `hitTest()` devuelve **el más cercano** dentro del radio, no el primero (las zonas de dos markers vecinos se solapan, ver arriba). El globo del clúster sale de `options.clusterHoverHtml?.(count)` con default `` `${count} temas` ``, y el `offset` del overlay es `radius - TEMAS_MAP_MARKER_HIT_PADDING` —el radio *visual* del target—, porque un clúster mide 30px y un marker 18px y con el radio del marker el globo caería adentro del círculo. Ojo al testear: los grupos **también** se arman con puntos fuera de la viewport (dos ciudades lejanas siguen a ~0px entre sí en cualquier zoom), así que `targets` trae objetivos fuera de pantalla; es inofensivo (el puntero nunca llega ahí), pero un test que busque "el primer target" puede agarrar uno invisible.
- **`map.renderSync()` entre el `fit` y el `declutter()`, no opcional.** El render de OpenLayers es asincrónico, así que en el `declutter()` de apertura el mapa todavía no pintó nunca y `getPixelFromCoordinate` devuelve `null` para todos los markers: un `declutter` sin píxeles no agrupa nada. Sin el `renderSync()` el spiderfy solo aterrizaba en el próximo `moveend`, que con capa base llegaba a los ~300ms (cuando los tiles resuelven y mueven la vista) pero **con `temasMapTiles: ''` no llegaba nunca** y los markers quedaban apilados para siempre. Es el mismo tipo de corte que el `map.updateSize()` que está justo arriba.
- **La capa base es OSM por defecto**, `temasMapTiles` la sobreescribe con cualquier plantilla `{z}/{x}/{y}` (ojo: `ol/uri.js` sustituye `{z}/{x}/{y}` / `{-y}`, no `{r}`) y `temasMapTiles: ''` la apaga y deja solo los puntos. En modo single el mapa también existe (el ítem se pide entero).
- **La atribución es de la capa base, no una etiqueta fija.** `temasMapAttribution` (default `TEMAS_MAP_ATTRIBUTION_DEFAULT`, el `&copy; OpenStreetMap` con link) es el crédito de *esos* tiles, y se inyecta como HTML para que el crédito pueda ser un link. El flag `showAttribution` de `_mountTemasMap()` = `temasMapTiles && temasMapAttribution` decide **las dos cosas**: si el `attributions` del `ol.XYZ` se pasa o se omite (pasarlo vacío dejaría el recuadro del control), y si el control `Attribution` va en `controls` o no. Con `''` no se muestra nada —no una cadena vacía en el pie, sino directamente la ausencia del control—, y con `temasMapTiles: ''` tampoco, porque sin capa base no hay tiles que acreditar (que es lo que ya pasaba antes de que la opción existiera: el control leía las `attributions` de las sources y no tenía ninguna). Los dos usan `=== undefined` y no `||` en el constructor, por el mismo motivo que `temasMapTiles`: un `''` explícito es la manera de apagar.
- **Teardown obligatorio.** `dispose()` no pasa solo: `_destroyTemasMaps()` se llama antes de vaciar la lista (`_renderTimeline` y `_renderApiLoading`) porque esas tarjetas pueden estar sosteniendo un mapa, y `map.setTarget(undefined)` + `overlay.setMap(null)` lo sueltan.
- **En los tests e2e** `e2e/helpers/network.js` stubbea `tile.openstreetmap.org` con un PNG transparente 1x1 y sirve `ol` desde `node_modules` por el route `/vendor/` de `example/server.js`, así que la suite sigue hermética. Para ver la capa por defecto sin tiles reales alcanza con el stub; `temasMapTiles: ''` no es un flag del demo, es una opción del constructor.

Como un `span` no es focusable, lleva `role="button"` + `tabindex="0"` y un `keydown` de Enter/Espacio (con `preventDefault()` para que Espacio no scrollee la página), y el hover/focus siguen saliendo del mismo CSS. **Seis cosas que costaría romper:** (1) **el enganche es por campo**: `_cardFilterGroup(CARD_CLICKABLE_FIELD)` devuelve el grupo solo si declara `cardClickable: true` **y** su `field` es `CARD_CLICKABLE_FIELD` (`'actores_principales'`, el único que `_buildProtagonistaHtml` sabe renderizar) y no estamos en `singleId`; sin grupo la tarjeta emite texto plano, así que la opción es inocua en cualquier otro campo. No hay nada que tocar en el server: `sortItems()` + `sortValue()` leen cualquier campo con `String()` y comparan natural, así que un sorter nuevo ordena en local y en API sin lógica por campo. Sin la opción `sorters` no hay UI de orden y el timeline usa `fecha_publicacion` desc como orden interno; la opción pública es `TimelineSorter { field, label, default? }` y no comparte normalización con `filters` (`_normalizeSorters` descarta `field`/`label` vacíos y `field` duplicado con `console.warn`).
- **Entender la nueva forma de declarar valores (`items`)**: un grupo **con `items`** muestra exactamente esos valores, en ese orden, y existe aunque ningún dato los traiga; un grupo **sin `items`** los deriva del dato y puede llegar a esconder el grupo entero si solo hay un valor (salvo que declare `allowEmpty`, que es justamente el caso donde ese único valor es el bucket vacío). `_resolveFilterItems()` (invocado desde `_normalizeFilters()`) convierte cada entrada en un `FilterDefItem`: `token` (los valores unidos por comas, que **es** el `input.value` y el query param), `tokens` (uno por valor, para comparar contra el ítem), `label` y `checked`. **La comparación es por token**: `_filterToken()` le aplica `String()` y `null` / `undefined` pasan a `'null'`, así que un `value: null` declarado matchea los ítems que no traen el campo; los arrays del ítem se expanden, así que un ítem puede contestar varios valores del mismo grupo. Un `value` **no puede contener coma** (rompe el CSV), y una declaración inválida descarta el grupo entero con `console.warn`, no el ítem suelto.
- **El bucket vacío de un filtro (`allowEmpty`)**: solo aplica a un grupo **sin `items`** (con `items` se ignora en silencio, porque ahí el bucket vacío es un valor declarado, `{ value: null, label: 'Sin tipo' }`). Con la opción, los ítems que no traen valor para el campo —token `'null'`, que `_filterToken()` ya produce— se ofrecen como **un valor más**, con el label fijo `"Sin valor"` (`FILTER_EMPTY_LABEL`), y **siempre último**: la rama de valores derivados de `_buildFilterCheckboxes()` lo mueve al final *después* del sort (conteo o `sortValues`), de modo que ni un grupo colapsado ni un `sortValues` lo dejan en medio. **.filter-select**, que es un multiselect con buscador, toma la fila completa del panel (`flex: 1 0 100%`) y se scrollea con `max-height`, sin "Ver más". El bucket vacío se **agrega al final** y la caja de búsqueda aparece sola con más de `FILTER_SELECT_SEARCH_MIN` (8) valores; las filas se ocultan por atributo, no se borran del DOM. Ojo con esto al tocar tests: el bloque `.filter-selects` va **antes** de las columnas, así que cualquier selector `.filter-column:nth-child(n)` del panel se corrió una posición (indexar sobre el NodeList de `.filter-column` en su lugar, como ya hace el helper `columnLabels()` de `test/filters.test.js` y `e2e/filters.spec.js`). En modo API la clave `"null"` de `facets[field]` se filtra igual que en local, así que el backend no cambia (y sin esa clave no hay bucket vacío que ofrecer).
- **Enrutar un grupo de filtros (`group`)**: son dos destinos, y el rename de `'estado'` a `'filtros_internos'` es parte del contrato público, no un detalle interno. `group: 'menu'` (default) mete el grupo en una columna del panel —la primera mitad de la declaración a la `column: 0`, el resto a la 1, repartido en `_normalizeFilters()`—; `group: 'filtros_internos'` lo manda al flyout rojo, que vive en el **toolbar interno** y por eso necesita `internalButtons: true`: sin esa opción `_buildInternalButtonsHtml()` no emite el wrap, y entonces `_attachFilterOptions()` deja el grupo sin slot (conserva la config y `_buildFilterCheckboxes()` lo saltea, no lo descarta). El tipo público es `FilterGroup = 'menu' | 'filtros_internos'` y la normalización es **estricta**: cualquier otro valor —incluido un `'estado'` de una versión anterior— cae en `'menu'` **sin `console.warn`**, así que el error se ve como un grupo que aparece en el panel en vez de como un filtro que no aparece. Si hay que cambiar el nombre otra vez, el rename arrastra: los 3 selectores del SCSS (`.filtros-internos-wrap` / `.filtros-internos-toggle` / `.filtros-internos-menu`, con sus `#id`, que también aparecen en `e2e/filters.spec.js`), las 3 refs de clase (`filtrosInternosWrap` / `filtrosInternosToggle` / `filtrosInternosMenu`), la key de `localStorage` (`tv-filtros-internos-filters`: renombrarla **descarta** el estado ya persistido de los consumidores), el `title` del botón (texto visible, "Filtros internos") y el `FilterGroup` del `.d.ts` distribuido.
- **El `label` de un grupo es opcional, y el flyout también lleva headers**: es la única entrada de `TimelineFilter` que **no** descarta al grupo cuando falta (`field` vacío, `type` no soportado o `field` duplicado sí lo descartan, con `console.warn`). `_normalizeFilters()` lo normaliza a `string` (ausente, `null` o solo espacios quedan `''`) y `_buildFilterOptionsHtml()` emite el `.filter-section` **siempre**, con el `.filter-header` adentro solo si hay label. El markup es **idéntico para los dos destinos**: el flyout de `filtros_internos` usa el mismo `.filter-section`/`.filter-header` que una columna del panel (por eso un grupo de "Sí/No" sin label también se lee: se ve igual de agrupado, solo que sin título). El SCSS comparte el estilo del header (`.filter-menu .filter-header, .filtros-internos-menu .filter-header`) y el separador va por `.filter-section + .filter-section`, ya no por `.filter-options + .filter-options`. No volver a la versión anterior, que en el flyout emitía un `.filter-options` pelado: `test/filters.test.js` y `e2e/filters.spec.js` cubren las dos caras (headers presentes / grupo sin label).
- **Tocar el corte "Ver más" de los filtros** (`maxVisible` por grupo, default `5`; la opción global `filtersMaxVisible` ya no existe): todo vive en `_buildFilterCheckboxes()` + `_buildFilterMore()`. El corte se calcula **solo si el grupo se colapsa** (`values.length > limit`, con `limit >= 2` resuelto por `_filterMaxVisible(field)`, que resuelve el `maxVisible` del grupo o el default). **El corte respeta el orden que el grupo ya tiene**: un grupo con `items` muestra los primeros declarados y esconde la cola, y solo un grupo **sin `items` ni `sortValues`** se reordena por **mayor conteo** (`counts[b] - counts[a]`; `sort` es estable así que los empates conservan el orden previo). Los valores de la cola se marcan `filter-option filter-option-extra` + `hidden` y el botón `button.filter-more` ("Ver más (N)" ⇄ "Ver menos") va al final del `.filter-options`; su handler alterna la clase `expanded` de `f.options`, que es lo que el SCSS usa para mostrar la cola (`display: none` / `display: flex` a la misma especificidad que `.filter-menu .filter-option`, porque el `display: flex` de autor le gana a la regla `[hidden]` de la UA; el atributo se mantiene igualado). **Un grupo con algún valor activo nunca queda colapsado** (`f.active.size > 0`), para no esconder un filtro aplicado. El estado de apertura vive en `_filterExpanded: Set<FilterField>` y **no** en el DOM, porque los checkboxes se reconstruyen (facets de API, re-scope de taxonomía) y el estado debe sobrevivir, igual que los toggles de taxonomías. El botón no llama a `_applyFilters()`: no es un filtro, es UI, y no debe re-renderizar el timeline. El corte es solo de los grupos `checkboxes`: un `select` no lo tiene (ver el punto siguiente).
- **El filtro `select` (`type: 'select'`)**: es el control para un campo con **muchos** valores, y es el segundo tipo del `FilterType` (`'checkboxes' | 'select'`, default `'checkboxes'`; cualquier otro valor descarta el grupo con `console.warn`). Tres reglas que no son obvias y que costaría volver a romper: (1) **el estado activo ya no vive en los checkboxes**: la única fuente de verdad es `FilterDef.active: Set<string>`, y los `input` de los checkboxes son una vista de ese set (`_syncFilterOptions()` los refleja). Un `select` no tiene checkboxes, así que cualquier consumidor que lea `f.checkboxes` para saber qué está filtrando está leyendo la mitad de la historia; para eso está `_filterActiveValues(f)`, y por eso la persistencia, `_buildQueryParams()` y `_syncFilterToggleState()` pasan todos por ahí. (2) **Un `select` no está en una columna**: `_normalizeFilters()` le deja `column: -1`, y `_buildFilterMenuHtml()` / `_buildInternalButtonsHtml()` lo sacan de la repartición en dos columnas y lo emiten primero, dentro de un `.filter-selects` (full-width, arriba de las columnas, y del mismo bloque en el flyout). Es el mismo `.filter-section` que los checkboxes, así que hereda el header y el separador. (3) **la lista es lazy y windowed**: `_ensureSelectOptions()` la arma en el primer click desde `select.values` (que ya están resueltos en `_buildFilterSelect()`, con sus labels en `select.labels`), pero **no la renderiza entera**: arma un `haystack` por valor en `select.haystacks` y deja solo los primeros `FILTER_SELECT_WINDOW` (50) matches en el DOM. El resto entra por `_extendSelectWindow()` — desde el `scroll` de la lista (`_maybeExtendSelectWindow()`) o desde el cursor del teclado (`_revealSelectCursor()`) — y `_extendSelectWindow()` **agrega** en vez de re-renderizar, justamente para no perder el `scrollTop` de una lista larga. `_renderSelectWindow()` sí reconstruye, y es lo que llama la búsqueda (`_filterSelectOptions()`), que corre sobre `select.haystacks` (**todos** los valores, no las filas) y deja el resultado en `select.matches`. Corolario: `select.options` son solo las filas renderizadas, así que nada que necesite "todos los valores" puede iterar `select.options` — tiene que ir por `select.values`/`select.matches`. El cursor del teclado camina `select.matches` (no las filas) y `_revealSelectCursor()` agranda la ventana si hace falta, con lo que <kbd>Home</kbd>/<kbd>End</kbd> alcanzan el primer y el último valor de los 400. `_ensureSelectOptions()` es además el seam natural para una carga por AJAX de los valores: no hay ninguna hoy, y no hay que tocar nada más para agregarla. El trigger reescribe los chips en `_renderSelectTrigger()`, y los muestra **todos** — no hay un "+N" que resuma la cola. Cada chip lo arma `_createSelectChip()`: un `span` con el label (el `…` lo pone `.filter-select-chip-label`, porque `text-overflow` solo funciona sobre un bloque con un nodo de texto directo y el chip es flex) y un `button.filter-select-chip-remove` con `tabindex="-1"`. Las dos cosas que no son obvias de ese botón: (a) su click hace `stopPropagation()`, porque el listener del trigger abre/cierra la lista y sin el corte quitar un valor abriría el desplegable; (b) el keydown del trigger arranca con `if (e.target !== select.trigger) return`, porque después de un click el botón queda enfocado y un <kbd>Enter</kbd> que suba hasta el trigger reabriría la lista (el corte por `target` cubre cualquier control anidado futuro, no solo este). El `tabindex="-1"` es deliberado: con cientos de valores, un tab stop por chip taparía el resto del panel, así que quitar por teclado se hace en la lista. El `<button>` anidado es HTML válido porque el trigger es un `div[role="combobox"]` y no un `<button>`. El cursor del teclado es una clase `.cursor` sobre la fila (`_renderSelectCursor()`), no un `focus`, porque las filas son `div`s y sin la clase se camina a ciegas; <kbd>Espacio</kbd> solo alterna si no hay buscador (si lo hay, la barra espaciadora es una barra espaciadora). El cierre por click externo vive en el `document.addEventListener` de `_bindBaseEvents()` y **corre antes** del cierre del panel, para que el click que cae en otra parte del panel no deje una lista colgando.
- **El ancho de los desplegables de filtros (`select` y checkboxes) — regla de SCSS, no de TS**: los dos menús (`.filter-menu` y `#filtros-internos-menu`) son `position: absolute` **sin `width`**, así que su ancho sale del shrink-to-fit, o sea del max-content de su contenido, y un solo valor larguísimo los estiraba hasta salirse de la pantalla (medido: 380px → 2069px en el panel y 200px → 3196px en el flyout) sin que el `text-overflow: ellipsis` de las filas llegara a activarse nunca, porque no había ancho disponible contra el que cortar. Son tres reglas y se necesitan juntas: (a) `.filter-select { width: 0; min-width: 100% }` — el bloque del `select` toma el ancho del padre (el que el panel ya tiene, su `min-width`) y saca su max-content de la cuenta; (b) `.filter-menu { max-width: min(560px, calc(100vw - 32px)) }` y `.filtros-internos-menu { max-width: min(360px, calc(100vw - 32px)) }` — el techo para las columnas de checkboxes, que **no** pueden auto-ajustarse como el bloque del `select` (son `flex: 1`, o sea que les conviene seguir creciendo con el contenido). **Nada de porcentajes ni `min()`/`calc()` en el corte de un label**: verificado en el browser que un `max-width: min(320px, 100%)` en `.filter-select-option-label` deja el menú en 1974px, porque el porcentaje no resuelve durante el cálculo del shrink-to-fit; solo un largo definido acota la contribución intrínseca. Y el texto completo nunca se pierde: el `title` de la fila (`opt.title`) y el del chip llevan el valor entero. Ojo con el `@media (max-width: 600px)` **de `.filter-menu`**: las declaraciones van **directas** en el `@media`, sin volver a nombrar la regla. Anidadas adentro de `.filter-menu` compilan a `.publicaciones-timeline-section .filter-menu .filter-menu`, un descendiente que ningún nodo puede ser, así que el bloque entero nunca aplicaba y en móvil el panel conservaba el `min-width` de escritorio y se salía de la viewport (mismo patrón que el `@media` de `.timeline-cards`; `.sort-menu` y `.filtros-internos-menu` lo tienen bien porque su bloque está fuera de la regla).
- **Tocar los facets (modo API)**: Los conteos son **estáticos**: se piden una sola vez con `GET {url}/facets` sobre la colección completa, sin `q` ni filtros, y `_apiFacets` no se vuelve a asignar. La lista (`GET {url}`) ya no los lleva; `_adoptLegacyApiFacets()` es el único fallback para backends que todavía los mandan en la respuesta. **El pedido es lazy y_cacheado**: nunca se llama a `_loadApiFacets()` directo, siempre a través de `_ensureApiFacets()`, que cachea la promesa en `_apiFacetsPromise` (incluso si el request falló, así que no hay reintentos). El enganche es **siempre en `_init()`**, en paralelo con la primera página: el facets no es solo del panel de filtros, también trae el `total` de la colección (contador del botón) y el `lastUpdated` (pie), y los dos se ven antes de que el usuario toque algo. El `if (this.api) void this._ensureApiFacets()` de `_toggleExpand()` queda como cache hit de seguridad, no como disparador. Los checkboxes se construyen **dos veces y solo dos**: una en `_init()` (sin conteos, para que los defaults de estado ya vayan en la primera request de la lista) y otra en el `.then()` de `_ensureApiFacets()` (que además parchea el contador con `_renderRelatedCount()` y el pie con `_renderLastUpdated()`, sin re-renderizar el timeline). Nunca en cada `_fetchPage()`: recrearlos en cada página borraría el estado de los filtros que no son de estado (`tonos_sociales`, `tipo_fuente`, `es_oficial`, `anio_publicacion`, `contenido`), que no se persisten. El rebuild no pierde estado igual: sin facets los grupos que **derivan** sus valores quedan ocultos (y con ellos `filterToggle`), así que no hay nada chequeable, los declarados (`items`) se muestran con los conteos en cero, y los de estado se restauran desde `localStorage`. El `catch` de `_loadApiFacets()` solo vacía `_apiFacets` si `_apiFacetsLoaded` es falso, para no pisar los facets legacy ya adoptados. El lado servidor vive en `example/server.js` (`STATIC_FACETS` + `STATIC_TOTAL` + `handleFacets`), y la ruta `/api/facets` tiene que declararse **antes** del branch `/api/:id`.
- **Los labels de los facets (`labels` en `/api/facets`)**: son el canal que separa **la clave con la que se filtra del texto que se muestra**. `GET {url}/facets` acepta un campo hermano `labels: Record<campo, Record<token, texto>>`, con **la misma clave que en `facets`** (el token crudo) y el texto lindo en el valor. Vive en su propio campo de clase (`_apiFacetLabels`, no dentro de `_apiFacets`) porque son dos cosas distintas: contar y mostrar. El token no cambia —el `input[value]`, `_filterActiveValues()`, `_buildQueryParams()` y la comparación contra los ítems siguen siendo el token crudo—, así que el label **solo se lee y nunca viaja**, y mandarlo es opcional (lo que no llega se muestra con su token, o sea el comportamiento de siempre). El único consumidor es `_apiFacetLabel(field, token)`, llamado desde `_filterOptionLabel()`: por ese seam pasan los checkboxes, las filas del `select`, los chips del trigger y los `title`, así que el canal cubre los dos controles sin duplicar nada, y `select.haystacks` sigue llevando `label + ' ' + token`, o sea que el buscador del `select` encuentra por las dos cosas. **El orden de precedencia es `_filterOptionLabel()` y no se cambia por lote**: `items[].label` declarado (lo que el cliente declaró explícitamente) → el bucket vacío de `allowEmpty` (que conserva su `FILTER_EMPTY_LABEL` fijo, porque el bucket es el mismo en todos los campos) → el `labels` del backend → `_filterLabelOf()` (`formatLabel`, o `"Sí"`/`"No"`). Consecuencia: el backend solo renombra los valores **derivados** (los de un grupo sin `items`), que son los únicos sin otra fuente de texto. Un label que no sea string, o que venga vacío/en blanco, se trata como ausente (`_apiFacetLabel` devuelve `''`) y el token se muestra como estaba. Se adopta en los mismos dos lugares que los conteos —`_loadApiFacets()` y el fallback legacy `_adoptLegacyApiFacets()`, que por eso también lee `labels` de `TimelineApiPageResponse`—, y el texto aparece junto con los conteos porque el panel se reconstruye en ese mismo `.then()`. El lado servidor vive en el `FACET_LABELS` de `example/server.js`: una **tabla estática**, no lógica por campo, que es la única forma de respectar el diseño de que el server solo tokeniza con `String()`.
- **Cambiar el contrato de la API**: `example/server.js` es la fuente de verdad de los endpoints, igual que el mock para los datos. Todo cambio de request o respuesta se aplica en el mismo commit al servidor de ejemplo + las interfaces de `src/TimelineViewer.ts` (`TimelineApiPageResponse`, `TimelineApiFacetsResponse`) + los tipos distribuidos (`npm run build`) + la sección "Modo API (servidor)" del README. En modo API **no hay campo `featured`**: el stack colapsado se arma con los primeros `items` de la página (`allCards.filter(capturado !== false).slice(0, featured_count)` dentro de `_renderAll()`), así que el servidor tampoco recibe el parámetro `featured`. `_apiFeatured` ya no existe. **Hay dos totales y cada uno tiene su fuente**: el `total` de la lista (búsqueda + filtros) llena `_apiTotal` → el status "Mostrando A-B de Y publicaciones" y `_hasMorePages()`; el `total` de `GET {url}/facets` (colección completa, sin `q` ni filtros) llena `_apiCollectionTotal` → el contador y el `relatedLabel(count)` del botón de expandir, escrito por `_renderRelatedCount()`. Igual que en modo local, donde el contador es `_allItems().length` (pool sin filtrar) y la paginación corre sobre `allCards` ya filtrado. **No hay fallback**: si `/facets` no manda `total` (o falla), el contador queda en `0`; usar el `total` de la lista daría un número que se mueve con cada búsqueda, que es justo lo que el contador no debe hacer. **La lista tampoco devuelve `lastUpdated`**: ese campo llega solo con `GET {url}/facets` (o por la opción `lastUpdated` del constructor), por lo que `_fetchPage()` / `_appendPageItems()` no lo leen y el pie "Actualizado por última vez el ..." lo escribe `_renderLastUpdated()`, extraído de `_renderTimeline()` justamente para poder parchearlo cuando llegan los facets sin re-renderizar el timeline (re-renderizar perdería una tarjeta ya expandida). **El orden es 100% del servidor**: los parámetros son `sort` (`asc`/`desc`, siempre enviado por `_buildQueryParams()`, y cualquier valor distinto de `asc` cae a `desc`) y `sortBy` (el campo, que es `_sortField`), y el componente **nunca ordena del lado del cliente en modo API** — renderiza la página tal cual la devuelve el endpoint. O sea que `sortItems(items, field, sortAsc)` + `sortValue()` de `example/server.js` tienen que reproducir exactamente el comportamiento del `_sortBy()` + `_sortValue()` local —comparación natural y estable por el campo activo—, en particular **los ítems sin valor para ese campo van al final en `desc` y al principio en `asc`**: invertir solo la comparación (y no el caso del valor ausente) pone los sin valor de un lado en modo local y del otro en modo API, que es la divergencia que replica la API de producción.
- **Paginación en modo API — append, nunca rebuild**: `_appendPageItems()` **no** llama a `_renderAll()`. Agrega solo las tarjetas nuevas con `_appendTimelineItems()` (el hermano de `_renderTimeline()` sin el `innerHTML = ''`) y les pasa los nodos a `_setupTimelineObserver(added)`. La razón es que `.timeline-item` nace en `opacity: 0` y solo aparece con `.visible` (salvo el caso `instant` de `_renderTimeline`, ver el bullet siguiente): un rebuild en cada página hacía que **toda** la lista repitiera su animación de entrada (el flash que reportó el usuario), además de perder el detalle ya inyectado en las tarjetas expandidas y recargar todas las imágenes. Rebuild solo donde es semánticamente correcto, o sea cuando lo que hay en pantalla ya no son los artículos en memoria: `_fetchPage(1)` (búsqueda/filtro/orden), el re-scope de taxonomía y —con `pagination`— cada salto de página. Al agregar tarjetas nuevas hay que respetar el orden del bloque final (`[tarjetas…, nuevas…, loadMore|paginator, status, footer]`): `_insertBeforeTrailing()` inserta antes del primer elemento entre `.timeline-load-more-item`, `.timeline-paginator-item`, `.timeline-status-item` y `.timeline-footer-item`; `_insertBeforeFooter()` (usada por la fila de status y los dos controles) solo mira el footer. El botón de "Cargar más" de API se **conserva** entre páginas (su handler lee `this._apiPage`/`this._apiLoading` en el momento del click, no por closure) y solo se elimina cuando `_hasMorePages()` pasa a `false`; el de modo local sí hay que re-crearlo, porque ahí el handler captura `start`/`end`. El stack de featured no se re-renderiza en el append: solo se ve con el timeline colapsado, y el botón vive adentro del timeline (`max-height: 0` cuando está colapsado), así que es inalcanzable en ese estado.
- **La transición de entrada y los placeholders (`instant`)**: `.timeline-item` nace en `opacity: 0` + `translateY(30px)` y solo aparece con `.visible` (`src/styles.scss`, 0.3s), una transición de clase, no de `@keyframes`. La agrega `_setupTimelineObserver()`, cuyo root es **el viewport** (no lleva `root`, así que `#timeline-cards` sigue siendo su propia caja con scroll), con `threshold: 0.1` y `rootMargin: '0px 0px 100px 0px'`; el stack featured no usa observer (`_setupObserver()` es código muerto) sino un rAF, con el stagger de la tabla `@for` de `nth-child` del SCSS. Los skeletons nacen **con** `visible` (`_appendTimelineSkeleton()`), así que no se animan —y ese mismo rAF es lo que hace que la animación **sí** corra en los demás casos: la clase tiene que aparecer en un frame posterior al de la inserción para que el navegador tenga un valor computado previo desde el cual transicionar. **Cuando `_renderAll()` baja los skeletons, las cartas no vuelven a entrar**: `_renderTimeline(cards, true)` (`instant`) las crea ya con `visible`, porque el placeholder ya ocupaba ese lugar y un slide encima se leía como un glitch. La pregunta "¿hubo skeleton?" se responde mirando el DOM **antes** de `_clearApiLoading()`, que es el mismo criterio de estado que usa `_renderStatus()`: no hay campo nuevo en la clase. Con `instant` el observer también se saltea (su único efecto es agregar `visible`, que ya está) y las filas de control no cambian porque van con `!important`. **Alcance: solo la rama API de `_renderAll`**, o sea los tres caminos con skeleton (primera carga, búsqueda/filtro/orden y salto de página del paginador). El stack featured conserva su slide escalonado y `"Cargar más"` y el modo local también, porque no pasan por `_renderApiLoading()`. Efecto colateral a tener presente: en API la carga inicial arranca con el timeline colapsado (`max-height: 0`), donde los skeletons del timeline no se ven nunca, así que las cartas de esa primera carga nacen visibles y el primer "expandir" las muestra en el sitio en vez de deslizarlas (el `max-height` de apertura sigue transicionando); para conservar ese reveal inicial, gatear `instant` por `this.isExpanded`.
- **Paginación numérica (`pagination: true`) — el otro modo de paginar**: con la opción activa **no hay "Cargar más"**: el control del final es `_renderPaginator()` ("Anterior | Página X de Y | Siguiente"), y `_renderAll()` elige entre los dos por `if (this.pagination)`. El criterio que separa los dos modos es **si la lista crece o se reemplaza**: "Cargar más" acumula páginas hacia abajo, así que el append sin rebuild de arriba es lo correcto; el paginador muestra páginas disjuntas, así que lo que hay en pantalla después del click ya no es lo que había, y por lo tanto el rebuild sí es lo correcto (mismo criterio que la regla de `_appendTimelineItems`). De ahí que en API reutilice `_fetchPage(page)` —el mismo call que ya hacen búsqueda/filtros/orden— y en local re-renderice desde `allCards`, que siempre tiene el pool filtrado entero. Los dos cursores son distintos y no se mezclan: `_page` es local, `_apiPage` lo posee el servidor. Todo lo que re-scopea o reordena el pool (búsqueda, filtros, orden, taxonomía) vuelve a página 1 por `_applyFilters()` en local y por `_fetchPage(1)` en API; `_goToPage()` recorta el destino en vez de rechazarlo, así que un resultado más corto aterriza en la última página y no en una vacía. El scroll al inicio lo hace `_fetchPage` con `if (page === 1 || this.pagination)`, delegando en `_scrollToTimelineTop()` (que tiene su propio corte por `fullpage`, ver el punto 5 del modo fullpage), para que la ruta de filters no cambie; `_goToPage()` lo llama **además**, en el acto y antes de esperar el request, porque en `fullpage` el `scrollTop` de la lista no scrollea y esperar el response dejaría la vista en el medio de la página que se está dejando. No compite con el de `_fetchPage` (que lo re-arma cuando aterrizan los datos): `_renderApiLoading()` corre sincrónicamente, así que para cuando `_goToPage` scrollea la lista ya es la nueva. **El stack de featured se congela en la página 1** (`_apiFeatured()` + `_apiFeaturedCards`): en API sale de los items en memoria, o sea de la página en pantalla, así que sin esto colapsar en la página 3 mostraría "las destacadas" de esa página. En local no hace falta porque `_featuredCards` ya es el pool completo. Con `pagination`, la fila de status **no muestra la carga, pero sí el conteo** (las líneas de error y de carga son exclusivas de API, porque en local no hay request propio que falle o que esperar; lo único que la fila escribe en local es el conteo): la carga la cubren los skeletons, porque el cambio de página es un request que **reemplaza** la lista y `_renderApiLoading()` se llama desde `_fetchPage()`, el trigger único de ese estado. Antes esa cobertura no existía y el pie decía "Cargando página N...", con las cartas de la página anterior todavía en pantalla; por eso `_renderStatus()` no tiene rama de carga para la paginación y su única línea de carga es "Cargando más publicaciones...", de `_appendPageItems()`, que solo existe sin `pagination`. El conteo es un **rango de posiciones**, no una cantidad: "Mostrando 11-20 de 55 publicaciones", que es lo que dice `_statusCountText()` (la única fuente del texto; devuelve `''` si no hay total o si una página volvió vacía, y el `end` se clampa al total porque un server puede devolver más items de los pedidos). Sale en los **cuatro** modos (local/API × paginador/"Cargar más"), y lo único que cambia entre ellos es de dónde salen los tres números: el **total** es `_apiTotal` en API (búsqueda + filtros, los manda el server) y `allCards.length` en local (el pool filtrado entero); el **cuánto hay en pantalla** es `allCards.length` en API —donde `allCards` **es** la página, o lo acumulado con "Cargar más"— y `_localDisplayCards().length` en local, porque ahí `allCards` siempre tiene el pool completo (y `_localDisplayCards()` es la misma lista que se le pasó a `_renderTimeline`, así que no puede desincronizarse de lo que se ve); y el **start** sale de `(_currentPage() - 1) * _pageSize() + 1` con el paginador y es 1 fijo con "Cargar más", porque la lista solo crece hacia abajo. Con `itemsPerPage: 0` el tamaño es 0 y eso colapsa el start a 1, que es lo correcto: la lista entera está en pantalla. No es redundante con el "Página X de Y" del paginador — ese dice cuál es la página y cuántas hay, el conteo dice qué tranche del resultado filtrado está en pantalla. En local la fila se escribe en la rama local de `_renderAll()` y también en el click de "Cargar más" (el único camino que hace crecer la lista sin pasar por `_renderAll()`); en API la escriben `_renderAll()`, `_appendPageItems()` y el `catch` de `_fetchPage()`. Un request fallido deja la lista vacía con el error, también al cambiar de página: el paginador se va con las tarjetas y no se vuelve a la anterior, hay que reintentar o recargar. `_apiPageSize()` con `itemsPerPage: 0` pide `API_UNBOUNDED_PAGE_SIZE`: el 0 documentado ("sin paginación") tiene que traer todo en una sola respuesta, y pedir una página chica dejaría al usuario con los primeros items y sin forma de pedir el resto.
- **Tocar las featured**: en modo local salen de `_featuredCards` (pool completo, armado en `_applyFilters()`); en modo API salen de `allCards`, o sea los primeros items de la página actual —salvo con `pagination`, donde se congelan las de la página 1 (ver arriba).
- **Tocar el mapa de "Temas destacados"**: ver `## OpenLayers — mapa de temas`. Si se cambia la lista de módulos de `ol` que importa `_loadOpenLayers()`, hay que actualizar **el importmap de `example/index.html`, y solo eso**: el `VENDOR_PACKAGES` de `example/server.js` sirve el paquete `ol` entero, así que un módulo nuevo sale sin tocarlo, y el stub de `tile.openstreetmap.org` de `e2e/helpers/network.js` es para los tiles, no para `ol`. Los tres puntos de entrada del feature son `_buildTemasHtml()` (markup + badges), `_bindTemasMapToggle()` (primer open, único que monta) y `_mountTemasMap()` (marcadores, los modos de `declutter` —spiderfy, clúster y el spiderfy sin tope de `zoom >= TEMAS_MAP_NO_CLUSTER_MIN_ZOOM`—, hit test de hover y de click); el teardown es `_destroyTemasMaps()`, llamado antes de vaciar la lista. La opción `temasMapTiles`, la opción `temasMapAttribution` y las constantes `TEMAS_MAP_*` son el único knob: no hay estado de mapa fuera de `_temasMaps`.
- **Tocar la vista del mapa general (`showFullMap`)**: la `section.publicaciones-fullmap-section` es **hermana** de `section.publicaciones-timeline-section` dentro de `.publicaciones-container` (la clase que el constructor agrega al container del consumidor), no un hijo del timeline: `.timeline-container` lleva `max-height: 0` mientras está colapsado, así que un mapa ahí no tendría alto en el modo normal. Su `height: 100vh` no es decorativo: los `top/bottom: 0` se resuelven contra el alto del contenedor posicionado que tenga alrededor —el del consumidor es de contenido, y con el timeline oculto al abrir el mapa mediría apenas la barra—, y sin una caja con resolución OpenLayers no tiene viewport contra el que hacer el `View.fit` (`.fullmap-canvas` repite el `100vh` porque es el target real de OL). Dos consecuencias del mismo reparto de ancestros: (1) **la base de `.timeline-item` cuelga de `.publicaciones-container` y no de la sección del timeline**, porque el markup se renderiza también en el `.fullmap-detail-body` de esta vista, que es hermano de la sección: moverla a `.publicaciones-timeline-section` deja la tarjeta del mapa general sin estilos base (le quedan solo los overrides de `.fullmap-detail-body`); (2) el piso `min-width: 680px` es de la rama del timeline, y es lo que hace que los `@container publicaciones (max-width: 600px / 610px)` del final del archivo solo corran por debajo de 660px de viewport (donde el `@media` correspondiente suelta el piso).
- **Los tres disparadores de `_refreshFullMap()` (y por qué el orden en `_applyFilters()` importa)**: la función se llama desde **exactamente tres** lugares —el primer click del botón, donde el mapa todavía no existe; el **final** de `_applyFilters()`, para un scope que cambió con el mapa en pantalla; y la re-apertura de un mapa ya montado con la bandera `_fullMapStale` encendida—, y agregar un cuarto sin mirar los otros rompe el contrato de "sin cambios de scope no se pide nada". Tres reglas que costaría volver a romper: (1) **el orden dentro de `_applyFilters()` no es libre**: en modo local `_refreshFullMap()` es síncrono (`this.api ? await this._fetchApiPoints() : this._fullMapPointsFrom(this.allCards)`, la rama local no espera nada), así que una llamada **antes** de recalcular `this.allCards` pintaba los marcadores del scope anterior mientras la lista ya mostraba el nuevo —ese era exactamente el bug reportado (marcadores que no coincidían con la lista filtrada)—, de ahí que la llamada quede después de `_renderAll()`; la rama API tampoco puede hacer early-return, porque `_schedulePageReload` deja corriendo el pedido de la lista y el refresh del mapa es independiente (su `/points` lleva los filtros, no la página). (2) **`_fullMapStale` es la única red de seguridad de la re-apertura**: `_bindFullMapToggle()` con el mapa ya montado hace `map.updateSize()` y llama a `_refreshFullMap()` **solo si la bandera está encendida**. La enciende `_applyFilters()` en cada cambio de scope, **también con el mapa cerrado** (ahí no hay nada que pintar, pero el set viejo queda colgado), y la apaga `_refreshFullMap()` recién cuando **acepta el set** —después del chequeo de `seq` / `_fullMapOpen` / `isConnected` y del `loaded === null`—, así que una respuesta descartada o un error la dejan encendida y el próximo open vuelve a preguntar en vez de dar por bueno un mapa de otro scope. Una re-apertura sin cambios no hace ningún request (ni el flash de "Cargando elementos del mapa…" de API). (3) **Abrir la vista es `fit`, siempre**: `_bindFullMapToggle()` encuadra los puntos actuales en las **dos** ramas de apertura, con `TemasMapHandle.fit()` —el mismo `fit` del montaje: `padding` de `TEMAS_MAP_FIT_PADDING`, tope `TEMAS_MAP_FIT_MAX_ZOOM`, `duration: 0`, zoom entero (el `View` lleva `constrainResolution: true`, ver el bullet de la sección OpenLayers), y un `updateSize()` previo porque la caja salió de `display: none`—: con scope sucio **después** de que `_refreshFullMap(true)` acepta los puntos nuevos (fittear los viejos sería encuadrar otro filtro), y sin cambios directo contra el set que ya está pintado. El pan y el zoom del usuario siguen vivos detrás del `hidden`, pero **no se retoman al reabrir**: "mostrar la vista" es mostrar el conjunto completo, no el recorte de la última visita (dejar la vista quieta era el bug de "al abrir el fullmap no encuadra los elementos"). Ojo con el alcance: un cambio de filtro **con el mapa abierto** sigue sin fittear —es el "No flash, no re-framing" del README—, así que `fit` solo lo pasa el toggle, nunca `_applyFilters()`. Alcance del scope: el mapa se arma con `this.allCards`, o sea el **pool filtrado entero y sin paginar**, no con la página en pantalla —con `itemsPerPage: 10` la lista muestra 10 tarjetas y el mapa reparte todos los que matchean, que es el diseño y no un bug—.
- **El estado de carga del mapa general (API)**: sigue **el mismo criterio que la lista** —lo viejo desaparece de inmediato y algo dice "cargando"—, pero sin skeletons: un mapa no tiene silueta que placeholderar, así que el estado es el velo de siempre sobre el canvas (`#fullmap-status`, `FULLMAP_STATE_LOADING` + `FULLMAP_LOADING_TEXT`, "Cargando elementos del mapa…"), que hasta ahora solo se escribía en la primera apertura. En `_refreshFullMap()` el mensaje se escribe cuando `!mounted || this.api`, y si el mapa ya está montado además se **cierra la ficha del punto abierto** (`_closeFullMapCard`, su marker acaba de irse) y se **vacían los markers** con `_fullMapHandle.updatePoints([])`: los del filtro que terminó no significan nada para el que está por venir y, con el server tardando uno o dos segundos, serían una respuesta vieja disfrazada de actual. La capa de tiles y la vista quedan (eso es lo que `updatePoints` preserva), así que se lee como "se está actualizando". Para que `updatePoints([])` pueda limpiar hay que **dejar de tenerle guard** `if (!next.length) return` (era la regla vieja de "un set vacío no hace nada"; el estado final lo decide igual `_refreshFullMap`). Tres detalles: (1) en **modo local** no se muestra nunca, porque `_fullMapPointsFrom` es síncrono (el único `mounted === false` local que lo ve es la primera apertura, donde se espera el import de `ol`); (2) `aria-busy` va y viene en `#fullmap-canvas` **desde `_setFullMapStatus`**, el único que lo toca, así que no puede desincronizarse del mensaje; (3) después del `await _mountFullMap` hay un segundo chequeo `if (seq !== this._fullMapSeq) updatePoints([])`, porque un filtro que cambia mientras `ol` se importa pinta el set viejo **después** del chequeo de `seq` que ya existía.
- **Tocar el estado expandido/colapsado del timeline**: El estado vive en `isExpanded` y solo se refleja en el DOM por `_applyExpandState()` / `_collapseExpandState()` (clases `expanded` en `section` y `timelineContainer`, rotación de `expandIcon` y `aria-expanded` del botón). `_toggleExpand()` solo hace el flip de `isExpanded` y delega en esos dos helpers: no agregar `classList.add/remove('expanded')` en ningún otro lado. La opción `startExpanded` (default `false`, sin persistencia) se aplica en `_init()` **antes** de `_applyFilters()`, porque el IntersectionObserver del timeline se engancha desde `_renderAll` y debe encontrar el container ya abierto (`max-height: 99999px`) en lugar de colapsado (`max-height: 0`). El preload de embeds va **después** de los datos, porque `_preloadEmbedLibraries()` deduce los tipos leyendo `this.allCards`. En modo API va enganchado a la promesa de `_fetchPage(1)`, para no correr en cada re-render; esa rama de `_init()` pide la primera página y los facets (que arman los checkboxes con los conteos) **siempre y en paralelo**, porque el contador y el pie ya se ven colapsados. `startExpanded` vale para cualquier modo, no solo single, y no cambia qué se pide: solo el estado inicial del DOM. La clase `has-taxonomy` es independiente del estado expandido: la agrega `_buildTaxonomySelect()` (solo cuando la fila del selector se conserva) y el SCSS la combina con `expanded` para ocultar `#remaining-count`, de modo que con taxonomías el único contador visible al abrir el timeline sea el de la píldora del selector.
- **Tocar el modo fullpage** (`fullpage: true`): es el único modo donde el timeline no se puede colapsar, así que tiene **cuatro cortes explícitos** en el TS y el resto es SCSS. (1) El constructor fuerza `this.isExpanded = this.fullpage || config.startExpanded === true` (por eso `fullpage` se asigna **antes** que `isExpanded` en el mismo bloque de asignaciones). (2) `_toggleExpand()` arranca con `if (this.fullpage) return;`: es la única red de seguridad, y cubre los tres caminos que llegan ahí (`#expand-toggle`, `#featured-cards` y `.featured-row`), por lo que además `_bindBaseEvents()` **no** bindea el click del botón — no volver a agregar la condición en cada listener. (3) `_buildLayout()` **no emite** el `div.timeline-resize-handle` y `_init()` **no** llama a `_initResizeHandle()`: si se llamara, leería `tv-timeline-cards-height` de `localStorage` y escribiría un `max-height` inline que pisaría el `none` del SCSS. Si se toca el resize handle, revisar las dos líneas: son la misma decisión. (4) `_renderFeatured()` y el loop de featured skeletons de `_renderApiLoading()` hacen early-return: en fullpage el stack nunca se ve (`expanded` lo colapsa a `height: 0`), así que no se construye nunca y `_featuredCards` (que `_applyFilters()` sigue calculando, barato porque son solo referencias) queda sin consumidor. Todo lo demás que consulta `featuredContainer` —los rAF que agregan `.visible`, `_clearApiLoading`, el click— es no-op solo por tener el contenedor vacío, así que **no** hay que guardarlo ni eliminar el `div#featured-cards` del markup (sacarlo deja `this.featuredContainer` en `null` y obliga a proteger 6 call sites). El `_getCardsHeightPx()` tiene su propio early-return a `window.innerHeight`: sin él, el `max-height: none` da `parseFloat('none') === NaN` y los skeletons de `_renderApiLoading()` caen al `RESIZE_MIN_HEIGHT`, o sea **un solo** placeholder. El layout en sí (barra sticky con fondo opaco, `min-height: 0` de `.featured-row`, `margin-top: 0` de `.timeline-container`, sin `max-height` en `.timeline-cards`, sin `expand-icon`) es un único bloque `&.fullpage` del SCSS, que va **después** de `&.expanded` porque comparte especificidad con él y el orden en el fuente es lo que resuelve. El offset de la barra sale de `--tv-sticky-top` (`:root`), por si el consumidor tiene un header propio. No aplica a single mode: `_renderSingleCard()` no pasa por `_buildLayout()` y ya renderiza una única tarjeta expandida. (5) **El scroll del timeline no es el mismo en los dos modos**: en el normal `#timeline-cards` es la caja con scroll (`max-height` + `overflow-y: auto`), pero en fullpage el SCSS la saca de su scroll box (`max-height: none; overflow: visible`) y scrollea la página, así que **`this.timelineCards.scrollTop = 0` es un no-op** — el mismo bug que hace que un cambio de página aterrice en el medio de la lista. Por eso todo "volver arriba" pasa por `_scrollToTimelineTop()`, que en fullpage busca el ancestro scrolleable con `_findScrollContainer()` (mismo helper que usa `_scrollToSection()`, y que también cubre que el consumidor monte el componente dentro de un contenedor scrolleable propio, con `window` como último recurso) y scrollea hasta dejar la lista **justo debajo de la barra sticky**, leyendo el offset del `getBoundingClientRect().bottom` de `.featured-row` en vez de una constante. Los dos call sites son la línea `if (page === 1 || this.pagination)` de `_fetchPage()` y el final de `_goToPage()`; no volver a escribir `scrollTop = 0` en ninguno de los dos.
- **El estado en la URL (`stateInUrl`)**: todo vive en cuatro métodos de `src/TimelineViewer.ts` (`_readUrlState`, `_applyUrlFilterState`, `_restoreUrlPage`, `_syncUrlState`) más `_urlFilters` / `_urlPage` / `_urlReady`, y el namespace es `URL_STATE_PREFIX` (`tv_`) con `URL_STATE_KEYS` para los fijos. Seis cosas que costaría volver a romper: (1) **`_readUrlState()` se llama desde el constructor, después de todas las asignaciones y antes de `_init()`**: lo que dice la URL tiene que estar en el primer render (el sorter, la píldora de taxonomía, el texto del buscador) y en el **primer** request de API; si se leyera en `_init` ya se habría renderizado la vista por defecto. (2) **El sembrado de los filtros va antes de `_buildFilterCheckboxes()`, y sin cruzar los tokens contra los valores del grupo** (`_applyUrlFilterState` asigna el `Set` crudo): en API un grupo derivado resuelve sus valores con `/facets`, que llega después de la primera página, así que sembrar "como se hace con `persist`" dejaría el **primer** request sin filtrar y el rebuild de los facets no lo corregiría (la lista ya está en pantalla). El cruce contra los valores reales pasa por `_seedFilterActive()`, que además da la precedencia **URL > `localStorage` > `checked` declarado**, con la URL ganando por ser lo más explícito y por sobrevivir a los rebuilds. Ese cruce es **por tokens, no por cadenas enteras**, y no es un detalle: un `value` declarado puede ser una lista (el `[null, false]` del "Sin descartar" del demo es **un** valor, cuyo token es `'null,false'`), y tanto el param de API como el `tv_*` viajan ese token tal cual, o sea como CSV — así que al releerlo de vuelta viene partido en `'null'` y `'false'`. Con una comparación de cadenas enteras ese checkbox queda sin tildar y el grupo filtra solo lo descartado, que es una lista vacía donde la había entera. La regla es que un valor queda activo cuando **todos** sus tokens llegaron, y de ahí sale también el sentido del CSV vacío (`?tv_campo=` = "ese grupo se limpió a propósito", `flat` vacío → nada activo). (3) **Un `tv_<campo>` no declarado se ignora en silencio, sin `console.warn`**: el caso es un link que trae los filtros internos de alguien con permisos abierto por alguien que no los tiene; `_normalizeFilters()` ya avisa de lo que está *declarado* y es inválido, que es otra cosa. Y un token que ya no existe no filtra: `_buildFilterCheckboxes()` se queda con la intersección, y si no queda nada activo el grupo no filtra, así que la lista nunca queda vacía por un link viejo. (4) **No se escribe durante el arranque**: `_urlReady` lo gatea, y `_init()` lo pone en `true` justo antes de `_restoreUrlPage()` (local) o del primer `_fetchPage` (API), que son los primeros momentos en que puede haber algo que corregir. La limpieza de los `tv_*` que no están en efecto la hace `_syncUrlState()` borrando **todas** las keys del prefijo antes de escribir las vigente: los params del consumidor no se tocan nunca. (5) **`replaceState`, no `pushState`, y sin `popstate`**: es una foto de la vista, no un historial (con `pushState` habría una entrada por tecla del buscador). La comparación para no escribir de más es `const before = url.search` **tomada antes** de tocar `searchParams`, porque `url.search` serializa en vivo y compararlo después siempre da igual. (6) **`tv_tax` viaja por label y `tv_page` solo con `pagination: true`**: el índice de taxonomía depende del deploy, y con "Cargar más" lo que hay en pantalla es un prefijo que crece, no una página. En API el selector no existe, así que ni se lee ni se escribe. La página se recorta con el mismo clamp de `_goToPage()` (local, en `_restoreUrlPage`) y, si la del link vuelve vacía del servidor, con un refetch a la 1 que también deja la URL corregida (API, en el `.then()` del `_fetchPage` de `_init`). En single mode (`singleId`) la opción es no-op: se desactiva en el constructor.
